1 Hear

Speech to text

Open a WebSocket, send one JSON config message, then stream raw audio at real-time pace. You get final text after each pause, followed by an <end> marker that tells you the caller finished their turn.

WSws://45.194.47.180:8900/transcribe-websocket
Model
ck-stt-live
First msg
{"api_key", "model", "language_hints": ["en","hi"]}
Audio in
16 kHz · mono · 16-bit PCM, binary frames, sent in real time. A 20 ms chunk is 640 bytes.
You get
{"tokens":[{"text":"…","is_final":true}]} after each ~0.7 s pause, then <end>
Languages
Keep ["en","hi"]. English, Hindi and Hinglish are detected per turn. Hints don't change the script.
Caller saysMera order kab aayega? Tracking ID bhi bhejo.
STT returnsमेरा order कब आएगा? Tracking ID भी भेजो।
Illustrative. Hindi comes back in Devanagari, English words stay in Latin script. Prompt your LLM for that mix.
Convert any audio file to the right format 
ffmpeg -i input.mp3 -ar 16000 -ac 1 -f s16le call.raw
2 Think

arjuna-3.5 LLM

A chat completions endpoint with the familiar messages format. It streams by default, which is what you want for voice: start speaking the first sentence while the rest is still being generated.

POSThttp://45.194.47.180:8815/llm/v1/chat/completions
Model
arjuna-3.5
Auth
Authorization: Bearer YOUR_KEY
Body
model, messages, max_tokens, stream
Streaming
On by default. Send "stream": false to get one JSON response.
Budget
10 requests/min per key, so make one call per caller turn.
Using an SDK? Point an OpenAI-style client at http://45.194.47.180:8815/llm/v1 and pass stream explicitly. Since the server streams by default, leaving it out can confuse clients that expect a single JSON body.
3 Speak

Text to speech

Open a WebSocket with your key and voice in the URL, send text as JSON, and read back raw audio frames. Pick a voice below and the snippets switch to it.

WSws://45.194.47.180:8080/v1/audio/stream?api_key=YOUR_KEY&voice=raju
Send
{"text":"…","context_id":"c1","flush":true}
Audio out
24 kHz · mono · 16-bit PCM, binary frames
Languages
English, Hindi and Hinglish, in all four voices
Budget
30 requests and 2,500 characters per minute
Mind the sample rates STT takes 16 kHz, TTS returns 24 kHz. Resample if you feed TTS output into STT or into a phone line.
Per key

Rate limits

Every key gets the same budget. Plan your demo around it, especially the LLM, which is the tightest.

LLM

arjuna-3.5
10requests / min
30,000tokens / min

About one turn every 6 seconds. Don't call the LLM on partial transcripts; wait for <end>.

STT

ck-stt-live
2parallel streams
30new streams / min

Two live callers at once. Keep one socket open for the whole call instead of reconnecting each turn.

TTS

4 voices
30requests / min
2,500characters / min

Roughly 40 characters a second. Keep replies short; set max_tokens low.

429Over the limit

Wait the number of seconds in the Retry-After header, then retry.

401Bad key

Check for spaces or a missing character. The same key works for all three services.

Call from your backend

The endpoints are plain http:// and ws://. An HTTPS web page can't open them, and a key in frontend code is public.

One key, one budget

Every teammate testing on the same key draws from the same limits. Coordinate before a live demo.

Retry politely

On 429, back off for Retry-After seconds. Hammering the endpoint only extends the wait.

No key needed
